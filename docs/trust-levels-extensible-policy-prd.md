# Trust Levels 可扩展策略 PRD

## 1. 文档信息

- 产品：`xypp/flarum-trust-levels`
- 目标版本：下一正式版本（建议 `v1.1.0`）
- 目标环境：Flarum 2.x
- 状态：待实现
- 范围：等级条件、自动升级、自动降级、管理员策略、等级图标和数据迁移

## 2. 背景与问题

当前扩展的策略逻辑包含固定等级边界：

- 自动升级代码要求下一级 `level < 4`。
- 自动降级只在当前等级为 3 时执行。
- 创建或编辑等级时，等级 4 及以上会被强制设置为 `manual_only`。
- 等级 3 默认允许降级，默认宽限期为 14 天。

这会导致等级 5、6 或以后新增的等级 7、8 无法按条件自动升级。等级数量本应由数据库配置决定，不应由代码中的某个数字决定。

## 3. 产品目标

1. 支持任意数量的信任等级，不设代码级最高等级。
2. 新等级默认可以自动升级，管理员可以明确将某个等级设为手动管理。
3. 自动降级按等级独立配置，不绑定等级 3。
4. 保留现有六个等级、用户组关联和用户当前等级，不破坏已有数据。
5. 等级图标采用固定的系统预设图标，与 Flarum 后台权限页面使用一致的图标按钮和视觉规范，不再要求输入 Font Awesome 类名。
6. 旧数据迁移后行为可预测，并且迁移可重复执行。

## 4. 非目标

- 本版本不重写条件采集器或条件表达式引擎。
- 本版本不删除用户组、不重命名现有等级、不重置用户等级。
- 本版本不允许普通用户修改等级策略。
- 本版本不把图标存储改成外部图片或上传文件。

## 5. 核心规则

### 5.1 等级排序

- 等级由 `trust_levels.level` 的整数值排序。
- 等级值必须唯一且非负。
- 等级 0 是基础等级，通常命名为“注册用户”。
- 当前等级的下一个等级，是排序后大于当前等级的最小等级。
- 当前等级没有下一个等级时，视为已达到当前配置中的最高等级，停止自动升级。

### 5.2 自动升级

- 下一级存在、`manual_only = false` 且条件全部满足时，自动升级。
- 不再使用 `nextLevel->level < 4` 或任何固定数字边界。
- 一次条件检查可以连续跨越多个已满足的等级，直到遇到条件不满足、手动等级或最高等级。
- `manual_only = true` 的等级不会被自动升级到，必须由管理员操作。
- 自动升级成功后更新用户等级、托管用户组和 `trust_level_changed_at`，并发送现有等级变更通知。

### 5.3 自动降级

每个等级独立配置：

- `allow_downgrade = false`：条件失效时保持当前等级。
- `allow_downgrade = true`：条件失效且宽限期结束后，降到上一个已配置等级。
- `downgrade_grace_days` 为 0 时不等待，条件失效后可立即降级。
- 宽限期从用户进入当前等级的 `trust_level_changed_at` 开始计算。
- `manual_only = true` 的等级不自动降级，即使历史数据中的 `allow_downgrade` 为 true，也必须在运行时视为 false。
- 等级 0 没有上一级，永不执行降级。

降级只处理当前等级，不重新计算更低等级的历史条件链；降级完成后由下一次条件事件或主动检查继续校正用户状态。

### 5.4 手动管理

`manual_only` 是明确的策略开关：

- 开启后禁止自动进入该等级。
- 开启后禁止自动离开该等级。
- 管理员仍可通过现有后台操作调整等级。
- 开启该开关时，后台应关闭或忽略自动降级相关控件，避免展示互相矛盾的配置。

默认值为关闭。新建等级 7、8 或更高等级时，不因等级数值自动变成手动管理。

## 6. 默认等级方案

以下是 LowSeek 当前六级体系的建议默认值。等级 0 保持现有“注册用户”含义，等级 1 至 6 使用组合条件。条件采用“全部满足”语义；空条件等级不允许自动升级。

| 等级 | 名称 | 建议图标 | 注册天数 | 主题数 | 回复数 | 获得点赞数 | 默认策略 |
|---:|---|---|---:|---:|---:|---:|---|
| 0 | 注册用户 | `fa-user` | 0 | 0 | 0 | 0 | 自动基础等级 |
| 1 | 信任等级1 | `fa-user-plus` | 1 | 1 | 3 | 0 | 自动升级 |
| 2 | 信任等级2 | `fa-seedling` | 7 | 3 | 10 | 3 | 自动升级 |
| 3 | 信任等级3 | `fa-shield-halved` | 30 | 8 | 30 | 15 | 自动升级，降级可选 |
| 4 | 信任等级4 | `fa-medal` | 90 | 20 | 80 | 40 | 自动升级，降级默认关闭 |
| 5 | 信任等级5 | `fa-star` | 180 | 40 | 180 | 100 | 自动升级，降级默认关闭 |
| 6 | 信任等级6 | `fa-crown` | 365 | 80 | 400 | 250 | 自动升级，降级默认关闭 |

说明：

- 主题数、回复数、点赞数应继续复用现有采集器的条件名称和统计口径。
- 删除、隐藏或被判定为无效的内容是否计入，必须由对应采集器统一决定，信任等级模块不重复实现统计。
- 以上数值是默认建议，后台仍应允许管理员调整。
- 等级 7 及以后不在代码中预置数值；管理员创建时填写条件即可。

## 7. 等级 7 及以后

新增等级的处理方式：

1. 管理员填写唯一等级值、名称、用户组和条件。
2. 系统按等级值插入排序，不要求连续编号。
3. `manual_only` 默认关闭，因此新等级默认参与自动升级。
4. `allow_downgrade` 默认关闭，避免新等级因条件波动导致意外降级。
5. 图标从预设图标列表中选择；预设不足时循环使用或扩展列表，不允许用户输入任意 CSS 类名。
6. 新等级成为当前配置中的最高等级后，自动升级在该等级停止。

## 8. 图标与后台界面

### 8.1 图标规则

- 删除创建/编辑表单中的自由文本图标输入框。
- 使用固定的 Font Awesome 图标预设列表，例如：`user`、`user-plus`、`seedling`、`shield-halved`、`medal`、`star`、`crown`、`gem`、`trophy`。
- 数据库仍保存完整图标标识，格式为 `fas fa-*`，以兼容现有数据。
- 旧数据中的合法图标继续显示；无法识别的值回退到 `fas fa-layer-group`。

### 8.2 视觉与交互

- 图标选择器使用 Flarum 后台权限页面相同的 `Button--icon`、图标尺寸、悬浮提示和焦点样式。
- 每个图标按钮必须有可访问名称和 tooltip。
- 当前选中图标要有明确的选中状态。
- 等级名称、等级值、用户组和条件继续使用现有表单布局。
- 不显示要求管理员手动输入 `fas fa-*` 的帮助文案。

## 9. 数据模型与迁移

现有字段继续保留：

- `level`
- `name`
- `icon`
- `conditions`
- `group_id`
- `allow_downgrade`
- `downgrade_grace_days`
- `manual_only`

迁移要求：

1. 不删除 `trust_levels` 记录，不重建用户组关系。
2. 将现有等级 4、5、6 的 `manual_only` 从自动强制值改为保留数据库当前值；仅对空值使用默认值 false。
3. 将现有等级 3 的降级配置保留，不再强制所有等级 3 开启降级。
4. 对空图标或无效图标写入预设回退图标。
5. 迁移应可重复执行，不产生重复等级或重复用户组关系。
6. 生产迁移前必须备份数据库和 Composer 锁文件。

## 10. 后端实现要求

### 10.1 `TrustLevelUtils::checkLevel`

- 移除 `nextLevel->level < 4` 条件。
- 只检查 `nextLevel->manual_only` 和条件结果。
- 将自动降级判断从 `currentLevel->level === 3` 改为 `currentLevel->allow_downgrade`。
- 保持 `manual_only` 优先级最高。
- 继续使用访问过的等级集合，防止异常配置造成循环。

### 10.2 `TrustLevelResource`

- 创建和更新时不再根据等级数值强制写入 `manual_only`。
- `allow_downgrade` 与等级值解耦。
- `downgrade_grace_days` 仅在 `allow_downgrade = true` 且 `manual_only = false` 时生效。
- 保留权限校验，只有具备管理权限的管理员可以修改策略。

### 10.3 前端编辑表单

- `allow_downgrade` 不再只在等级 3 启用。
- `downgrade_grace_days` 根据当前等级的 `allow_downgrade` 和 `manual_only` 状态启用/禁用。
- `manual_only` 对所有等级可用，等级 0 可隐藏或保持禁用，因为基础等级不应被手动策略锁死。
- 保存时提交真实策略值，不根据等级数字覆盖用户选择。

## 11. API 行为

- 等级资源返回真实的 `allow_downgrade`、`downgrade_grace_days`、`manual_only` 和图标值。
- 创建接口拒绝重复等级值、负数等级值和无效用户组 ID。
- 更新接口不能修改已有等级的用户数据，只修改策略和展示配置。
- 删除等级前检查是否有用户处于该等级；有用户时要求管理员先迁移用户或明确确认。

## 12. 验收标准

### 自动升级

- 配置等级 0 到 6 后，用户满足条件可依次自动升级到等级 6。
- 创建等级 7 并配置条件后，满足条件的用户可自动从等级 6 升到等级 7。
- 创建等级 8 后不需要修改 PHP/TypeScript 代码即可参与升级。
- 设置某等级 `manual_only = true` 后，用户满足条件也不能自动进入该等级。
- 当前等级没有下一级时，不报错、不循环、不重复发送通知。

### 自动降级

- 任意等级开启 `allow_downgrade` 后，条件失效会按宽限期降到上一级。
- 关闭 `allow_downgrade` 后，条件失效不会自动降级。
- `manual_only = true` 时不会自动降级。
- 宽限期为 0 时立即生效，宽限期大于 0 时按 `trust_level_changed_at` 计算。

### 数据和兼容性

- 线上现有六个等级、名称、图标、用户组和用户等级保持不变。
- 迁移前后 `trust_levels` 记录数量一致。
- 旧图标仍可渲染，空或非法图标能回退到预设图标。
- 后台权限页面风格的图标选择器可键盘操作，并有 tooltip 和选中状态。

### 生产验证

- 执行 `php flarum migrate`、`php flarum assets:publish` 和 `php flarum cache:clear` 成功。
- Flarum、queue、realtime、scheduler 容器均保持运行。
- 后台等级页面无 JavaScript 控制台错误。
- 普通用户无法修改等级策略，管理员可以修改并保存策略。

## 13. 发布与回滚

发布前：

1. 备份数据库。
2. 备份 `composer.json`、`composer.lock` 和扩展配置。
3. 在本地完成 PHP、TypeScript、构建和迁移测试。
4. 创建版本标签并发布 GitHub Release。

回滚：

- 回退到上一 Git 标签并重建容器。
- 如迁移只增加字段或修正策略值，优先使用反向迁移；禁止直接删除用户等级数据。
- 数据库恢复必须在确认备份完整后执行。
